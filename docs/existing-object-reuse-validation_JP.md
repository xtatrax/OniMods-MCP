# 既存実体の再利用と支持未評価の区別

既に一致する設備や設計図がある予行では、新しい建設を行わずその実体を再利用できるとき、従来どおり`valid=true`、`alreadyPresent=true`を返す。この値を「現在の支持を再検査して成立した」と解釈しないよう、該当する早期再利用応答へ検査範囲を添える。

```json
{
  "valid": true,
  "alreadyPresent": true,
  "validationScope": "existing_object_reuse",
  "support": {
    "status": "not_evaluated",
    "currentValid": null,
    "nativeFoundationValid": null,
    "requiresSupportCompletion": null
  }
}
```

`valid`はこの再利用分岐の許容結果であり、支持成立・稼働・通電・工事完了の保証ではない。支持の3項目はキーを保持して`null`を返す。未評価を`false`、`true`、正常値へ補わない。

## 適用範囲

- 対象は`TryPlanOne`の、既存実体が配置・種類・指定素材と一致し、そのまま再利用を返す早期分岐。既存の`alreadyBuilding`／`alreadyBlueprint`、実体ID、形状照合を保持する。
- 支持を再評価したように見せるためのnative getter・UI操作・再初期化は追加しない。既存の再利用条件と実行結果も変えない。
- 新規配置は従来の支持検査を続ける。支持不足の拒否や、評価済みの`support`を新しい未評価結果へ置き換えない。
- タイル交換、既存設計図の即時完成など、早期再利用より先に処理される専用分岐は今回の追加対象外。全予行応答の統一ではない。
- 回転設備を参照する際は、実体geometryの左下と本体原点を区別する。IDをアンカーにする既存予行は、本体原点を新しい配置の左下入力として使う[既存契約](build-preview-id-anchor_JP.md)を維持する。

## 検証と限界

公開側自身の実製品親関数・実体照合を結んだホスト回帰30条件と既存回帰、旧親関数全文のコンパイル成功後の意味的負対照、本体参照ビルド0警告0エラーを確認した。rawな応答辞書を実際のwire設定でシリアライズし、3つの未評価キーが欠落せず`null`として残ることも照合した。native geometry・支持判定などの協調部分はホスト代替入力であり、ホストだけで本体の挙動を受入済みにはしない。

公開版自身のDLL・固有ID・専用設定先を照合し、停止中の完成`LadderFast`と回転した完成設備の再利用で、従来の再利用フラグ・同一実体・形状、検査範囲と3つの`null`キー、観測セルと停止時計の保持を確認した。新規配置の予行では従来のnative支持検査を維持する。確認付きサンドボックスで試験設備と支持セルを準備し、短い進行後に停止して確認した結果である。

設計図の再利用はホスト試験のみ。試験設備の即時設置を、通常工事の搬入・完成や通常採掘での支持撤去の確認へ代用しない。全専用分岐・全native callbackの非変更や、支持関係全体の対応完了へ一般化しない。開発側の支持影響予測は今回の公開差分へ含めない。

保存せず通常終了し、元の導入物・有効設定・保護データと停止状態へ復帰した。個別保存先・実体ID・座標・生応答・私有補助と開発履歴は公開差分へ含めない。
