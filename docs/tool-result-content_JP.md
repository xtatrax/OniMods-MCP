# 通常結果と付帯Contentの識別

ツール応答の `content` 配列では、各テキストブロックの `_meta["onimcp.contentKind"]` を使って種類を識別する。本文の先頭文字列、JSONのキー、配列の位置から種類を推測しない。

| 値 | 内容 |
| --- | --- |
| `tool_result` | 通常の結果本文。`isError=true` のエラー本文も含む |
| `printing_pod_policy` | 製造ポッドの任意ポリシーによる付帯案内 |
| `notification` | ミドルウェアの通知 |
| `legacy_alias_warning` | 旧ツール名・別名の非推奨警告 |

`type`、`text`、Contentの順序と `isError` は従来のまま保つ。旧別名の警告は従来どおり先頭へ入るため、`content[0]` が通常結果であるとは限らない。分類情報に本文を複製せず、`structuredContent` へ大きな結果を二重化しない。MCPの [TextContentスキーマ](https://modelcontextprotocol.io/specification/2025-06-18/schema) が認める任意の `_meta` を利用する。

クライアントは全ブロックを順番どおり保持し、既知の種類ごとに参照する。未知の種類や `_meta` の無い古い応答は捨てず、未分類として保持する。通常結果が複数なら、1件へ連結・正規化せず各本文を保つ。JSONではない本文や配列・nullも、分類のために書き換えない。

この追加情報だけで既存クライアントの解析方法が更新されるわけではない。単一Textだけを解析するクライアントは従来の本文を利用できるが、複数Contentや旧別名では分類への対応が必要になる。案内の本文は残しており、メタデータだけを読んで案内内容を省略する変更ではない。

## 製造ポッドのポリシー

既定OFF。OFFでは付帯ポリシーを追加しない。ONでは既存の「補給品の受取または全拒否で決着する」という案内を保持する。自動受取、複製人間の自動選択、ポリシーによる一時停止は行わない。

再注入時に取り除くのは、そのミドルウェアが同じプロセス内で作成した付帯ポリシーだけである。通常本文が `{"printingPodSelection":...}` で始まっても除去しない。内部の所有フラグはJSONへ出さず、本文や外部から与えられた `_meta` を所有証明として使わない。

## 候補を取得できていない場合と0件の区別

`building_control domain=side_surface surface=facility kind=printing_pod action=list_rewards` は、対象に一致する既存の本体画面キャッシュだけを観測する。読取で画面を開く・候補を生成する・要件delegateを実行することはない。画面を開く操作は、従来どおり明示的な `open_immigrants confirm=true` で行う。

| `candidateObservation.status` | `rewardCount` の意味 |
| --- | --- |
| `unknown` | 取得不能・対象不一致など。件数は `null` |
| `not_materialized` | 本体のready=trueだが対象の候補一覧は未取得・未生成。件数は `null` |
| `generation_pending` | CarePackage候補の情報が未確定。件数は `null` |
| `no_ready_offers` | 現在は受取可能な候補なし。古いキャッシュを除外し0件 |
| `materialized` | 対象一致の非空キャッシュとCarePackage情報を確認した件数。補給品がない候補群なら0件 |

`reason/source/totalCount/carePackageCount` は観測根拠を示す小さな情報であり、候補配列は `rewards` に一度だけ返す。画面が閉じているだけでは既存キャッシュを未取得と決めつけない。Immigration自体を取得できなければ `available=null` とする。

互換性に注意するフィールドは、従来の真偽値・数値に `null` が追加される `available/rewardCount/requirementMet/claimable` である。受動読取では要件・受取可否を再評価せず、候補の `requirementMet` と `claimable` は `null`、`claimabilityStatus=not_evaluated` とする。`rewards=[]` だけで既知の0件と判断しない。

一覧の `index` と受取の `rewardIndex` は、同じ対象画面の候補順を使う。古いstatic global候補を選択元に混ぜない。受取・全拒否は確認条件と本体の選択・確定・後片付け経路を保つ。受理と完了を混同せず、応答後の候補状態と画面の後片付けも照合する。

## 検証方法と範囲

実DTO・ミドルウェア・レジストリをリンクし、本文保全、内部所有フラグ、ON/OFF、通知、エラー、read/write、先頭の旧別名警告を検査する。候補状態と選択順は実取得コードをリンクした試験で確認する。旧実装の正確なソースを差し替える比較試験は、コンパイル失敗と意味的な検出を区別する。

実機では各版自身のDLLを使い、停止した試験セーブの初回ロードと再ロードで確認する。実際のHTTP応答の全Contentを分類し、候補の取得前、通常UIによる生成後、受取／全拒否後を照合する。設定は通常の設定ページから切り替え、非対象設定・保護セーブ・停止時刻・既存画像の保持と、試験終了後の復帰を確認する。

ホスト上の代替境界を、すべての実機状態の観測と同一視しない。生成途中、受取可能だが複製人間だけの候補、取得APIの欠測などは、実際に観測できた範囲を別記する。外部の既存クライアント自体の改修を、このMOD側の分類追加や試験クライアントによるHTTP確認へ含めない。

## 限定的な実機受入と残る境界

両固有IDの初回・通常再ロード後で、実HTTPクライアントが全Contentを保持・分類することを確認した。候補取得前の `unknown` と件数 `null`、明示的な通常UI操作後の `materialized` 1件、受取または全拒否後の `no_ready_offers` 0件を区別した。ON/OFF、read/write、旧別名警告、エラーと通知を含む複数Content、ONの案内本文保持とOFFの付帯案内なしを照合した。既存の外部クライアント自体は変更していない。

`not_materialized` の確定状態、生成途中、取得APIの欠測、受取可能だが複製人間だけで補給品が0件の状態は、ホスト試験の境界であり実機では未観測である。これらの条件を実機で確認した成功記録とは扱わない。

実ソースの回帰試験、POと実行時翻訳の対応確認、両版の本体参照ビルドは成功した。旧実装の比較負試験では、ビルド失敗ではなく本文削除と未取得値の意味の差を検出した。

試験終了時は元導入物・設定・保護セーブ・共有保存・既存画像・他MOD/DLCと開始時の未起動状態へ復帰した。保存先選択は通常の原本ロードで戻し、本体が記録した採番値を採用した。preferencesを直接書き戻したり、異なるセーブ間の採番値へ単調増加を要求したりしていない。
