# 仮想操作の件数・部分成功・未取得値

結果集計の修正と、検証した範囲を記録します。

仮想操作は、SEARCH/REPLACE の編集ブロック、子コマンド、ゲーム本体の結果、地図上の要求セルという複数の段階を通ります。各段階の件数をゲームの変更数として合算せず、返された根拠と単位を分けて扱います。成功した操作の一部と失敗が混在した場合も、内側で確認できた進捗と `changed` を外側へ残します。

## 段階ごとの単位

| 応答・項目 | 意味 | 読み取れないこと |
| --- | --- | --- |
| SEARCH/REPLACE の `applied` / `appliedUnit=edit_blocks` | 成功扱いで実行を終えた編集ブロック数。成功扱いのブロックにも部分結果が含まれる場合がある | ゲームの変更数、完全に充足した要求数 |
| `ops/*.md` の `executedCommands` | 実際に呼び出した子コマンド数。呼び出し後に失敗したものも含む | 成功数、変更数 |
| `ops/*.md` の `applied` / `appliedUnit=legacy_child_counter` | 従来の子結果カウンター選択による集計。互換性のため維持 | 統一単位の変更数。読取でも値を持つ場合がある |
| 地図の `changedCells` | パッチが変更を要求したセル数 | 実際に変化した地形や建設物の数 |
| 地図の `executedCells`、建設グループの `applied` | 本体の結果と対応を確認できた、要求を満たす地図セル数。未取得があれば `null` | 新しく置いた設備数、物理的な占有セル総数 |
| `world_editor batch` の `applied`、`mutatedSteps` | 既存のバッチ集計を維持した値。子の従来カウンターや、変更系として分類されたステップの成功扱いに基づく | 共通単位の変更数、実際に変化したステップ数 |

建設では、複数の要求セルが設備1台のアンカーへ対応する場合があります。逆に、設備1台を1セルのマーカーで要求する場合もあります。要求セル数は元のパッチに基づき、設備の全占有範囲へ拡張して数えません。

## 確認できた進捗と不明な進捗

地図の `cellProgress` は次の形です。

```json
{
  "unit": "requested_map_cells",
  "requested": 3,
  "satisfied": null,
  "knownSatisfied": 1,
  "unknown": 1
}
```

この例は、要求3セルのうち1セルの充足が確認でき、1セルは未判別であることを示します。残り1セルは未充足として扱われます。未判別を未充足のゼロへ置き換えません。

- `requested`: 元のパッチで要求したセル数。
- `knownSatisfied`: 本体の結果との対応が確認できた充足セル数。
- `unknown`: 充足したか判定できないセル数。
- `satisfied`: `unknown=0` のときだけ確定した充足セル数。それ以外は `null`。
- `completionKnown`: 未判別がないことを示す。すべての要求を満たしたという意味ではない。
- `remainingCells`: 充足数が確定した場合の未充足セル数。未判別があれば `null`。

対応付けでは、本体が返したアンカー、対象設備・ワールドの情報、元の要求セルを照合します。結果の欠落、不正な型、対象の不一致、重複などで対応が確定しなければ不明のまま残します。本体から返された `planned` 等の総数だけで充足を補いません。実行予算で未実行となったアンカーに属する要求セルは、充足数へ加算しません。一方、実行したアンカーと元マスク全体の対応を確認できる場合は、その設備が満たす元の要求セル全体を数えます。切り詰め後のマーカー数や設備の全占有数へ、要求セルの単位を置き換えません。

`alreadyPresent` 等により、既存の設備や設計図が要求を満たす場合があります。充足数と新しい変更の有無は別です。`next=complete` は、その応答で要求の充足を確認でき、失敗や部分結果が残らない場合に限ります。それ以外は地図の再取得と新しいパッチを案内します。古いパッチをそのまま再送しないでください。

## `changed` と子結果の根拠

`changed=true` は、その段階で変更の根拠を確認できた場合です。`changed=false` は変更なしを確認できた場合、`changed=null` は判断する根拠が足りない場合です。集計では、1件でも確認済みの変更があれば `true`、すべて変更なしと確認できた場合は `false`、変更なしと不明だけが混在する場合は `null` を返します。

各子結果の `nativeOutcome` は、その階層が受け取った子の JSON から、型を確認できた情報を残します。外側のバッチでは、子がラッパーの応答である場合もあります。名前だけでゲーム本体の直接観測と解釈しないでください。

| 項目 | 意味 |
| --- | --- |
| `observed` | 子結果を JSON オブジェクトとして取得できたか。ゲーム状態を再取得したという意味ではない |
| `changed` | 子が明示した真偽値。型違い・欠落は `null` |
| `counters` | 対象項目のうち、非負の整数として確認できた値。実際のゼロを保持し、未取得・不正値をゼロで補わない |
| `countUnit` | 一般の子カウンターについて単位を推定しないため `null` |
| `reasonCode` | 結果が取得できない場合は `native_result_unavailable`、対象項目に不正な型などがある場合は `invalid_native_fields` |

地図建設では、対応する本体の個別結果にある配置・完成等の明示的な根拠も使います。単なる `succeeded` やカウンターの増加から、新規変更を推測しません。

## 失敗と部分成功

失敗した応答から、すでに確認できた充足や変更を消しません。外側の編集・バッチが失敗していても、子の `changed=true` や部分結果を参照できます。一方、すべてが施工前に拒否され、変更なしが確認できる場合に、失敗件数だけを理由として部分成功にしません。

`ok`、`partial`、`changed`、充足数は別の項目です。`allowPartial` を使って成功扱いで返った結果でも、すべての要求を満たしたとは限りません。エラー後に再操作する場合は、詳細な子結果と最新のゲーム状態を確認してください。

## バッチで完全な子結果を取得する

既定のバッチ結果は、`text` の先頭900文字と必要に応じた省略記号・`truncated`・`totalChars` を返します。大きな子結果を常時全文へ展開しません。

進捗メタデータを持つ子結果について、対象ステップ自身へ JSON の真偽値で `"detail": true` を指定すると、そのステップの `result` に子結果の文字列全文を追加します。これにより、子結果に含まれる成功済みIDや `remainingAction` 等の再操作に必要な情報を、抜粋制限なしで確認できます。これらの項目が子結果にない場合、新たに作りません。

親バッチだけの `detail=true`、文字列の `"true"`、進捗メタデータのない無関係な読取では、この追加を有効にしません。全文は文字列なので、必要な階層だけ JSON として解析してください。`text` の既定の抜粋も残ります。

## 実行経路と検証の境界

この仕様は結果の保持・対応付け・集計を対象とします。ゲーム本体への引数、呼び出し順序、通常UIの委譲先、確認・dryRun・権限のガードを変更するものではありません。設計図の設置を設備の完成や通電・流量の確認として扱いません。

ホスト側では、実際のラッパーをリンクして合成した本体境界の結果を与え、単位の分離、欠落・型違い、部分結果、既存物の充足、予算による未実行、詳細取得の条件を検証できます。ゲーム本体の配置判断、個別結果の実際の形、セーブ後の維持、公開版への配備はホスト境界の外です。
