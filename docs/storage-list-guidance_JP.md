# 収納操作ファイルの一覧例

`/active/ops/storage.md` のコメント付き例は、現行の `building_control domain=storage action=list` を使う。旧 `domain=side_surface surface=storage action=status` は現在のrouterで未対応だった。例は `limit=3 detail=true` を明示し、最大3設備の一覧を操作ファイルの子結果へ保持する。読取ページを開いただけではコメント付き例を実行しない。

ここでの `detail=true` はops応答へ引数と子結果を残す指定で、個別収納の `action=detail` や `storageScope` を指定した意味ではない。既存のStorageを持つ完成設備一覧であり、所持アイテムの詳細は省略する。3は返す設備行数の上限で、内部の全設備探索量・タグ数・応答バイト数の上限ではない。既定primaryと明示all_components、フィルター書込・native UI範囲等の契約は変更しない。

開発版と公開版のそれぞれ自身の既存OperationResults回帰と本体参照0警告0エラー、配備DLLの停止実機で、生成本文から例の1行を取得して構文予行し、そのまま実行した。一覧3設備は別の直接読取と同じ例の反復に一致し、6時計項目・報告カメラ・元セーブと固有設定先／所有パッチを保持した。保存・時間進行・フィルター変更・在庫移送を要求せず通常終了し、元の導入物・設定・保護セーブ・他MOD／DLC・共有データ・既存画像と未起動状態へ復帰した。公開版固有の設定先・所有パッチID・重複なしも独立照合し、切替時のMOD不一致は観測した対象を通常のOK経路で一回確定して停止を保った。

操作ファイルの `applied=1` は編集ブロック数、子の `applied=0` は既存カウンター契約であり、収納の変更件数ではない。子の実行は1コマンド、`changed=null` は不明のまま保持する。新しいホスト試験は追加せず、既存回帰と実案内の実行を根拠にする。この例以外の案内・全編集経路・native UIや収納scope全体の新たな受入へ一般化しない。
