# 実績・勝利条件のキャッシュ読取契約

コロニー実績一覧と製造ポッドの勝利条件は、ゲームが既に保持している達成・失敗フラグと定義の情報を読み取ります。読取要求によって条件を再評価したり、要求ごとの進捗を生成したりしません。Steamアカウントの解除状態とは別の情報です。

## コロニー実績一覧

`world_editor action=read path=/active/colony/achievements.oni` の既存の引数と通常項目を維持します。

| 引数 | 契約 |
| --- | --- |
| `achievementDetail=brief` | 既定。ID・名称・状態・達成／失敗フラグ・勝利条件フラグを返す |
| `achievementDetail=full` | 説明と要求型の一覧を追加する。要求の進捗は評価しない |
| `achievementStatus` | `all`（既定）／`completed`／`incomplete`／`failed`／`unknown` |
| `query` | IDまたは名称の部分一致。大文字小文字を区別しない |
| `limit` | 1〜200。既定はbrief100／full10 |

`counts` は定義の無効・セーブ適合性による除外後、状態・検索条件による絞込前の件数です。`matched` は絞込後、`returned` と `truncated` は件数制限後の結果を示します。

一覧の `source` は `SaveGame.ColonyAchievementTracker.achievements`、`stateMode` は `cached_no_reevaluation` です。個々の `completed` と `failed` は、対応する既存キャッシュの `success` と `failed` を保持します。対応する記録がなければ両方とも `null`、状態は `unknown` です。未取得を未達成や失敗なしで代用しません。

状態の分類順は、記録なしなら `unknown`、`failed=true` なら `failed`、それ以外で `success=true` なら `completed`、残りは `incomplete` です。両フラグが同時にtrueの場合は失敗側へ分類し、生の両値はtrueのまま保持します。`counts` と状態絞込にも同じ分類を使います。本体の実績画面が同期処理で失敗表示を後から適用する順序へ合わせた分類であり、画面の現在の描画結果を読み取った値ではありません。

## 必要時だけ実績画面の既存キャッシュを読む

一覧に `includeAchievementUi=true` を指定すると、`uiObservation` を追加します。省略／falseでは画面を読まず、このキーも追加しません。brief/full・状態絞込・検索・limitを適用した後の返却IDだけを照合し、画面側の全IDを別途列挙しません。通常の一覧・件数・分類と画面観測は分けて保持します。

| 項目 | 意味 |
| --- | --- |
| `source` | `existing_retired_colony_info_screen_cache` |
| `status`／`reasonCode` | 既存画面の観測可否と機械判別用の欠測理由 |
| `screenOpen` | 本体の有効状態・階層activeの観測。未取得はnull。画面上の遮蔽や実ピクセルの可視性は判定しない |
| `currentColonyVerified` | 常にnull。画面には現在のセーブとの対応を確定できる保持情報がない |
| `items` | 返却ID順の既存ウィジェット観測。画面が未生成／閉鎖／不整合ならnull、対象IDが0件と分かる場合は[] |
| 各行の`toggleState` | 本体が保持する生の表示番号。欠測はnull。番号2だけで未達成と失敗を区別しない |
| 各行の`tooltipStrings`／`tooltipStringCount` | 本体が既に用意したローカライズ済み文字列と元件数。未取得はnull、既知0件は[]／0 |
| 各行の`tooltipTruncated` | 元の文字列数・長さに対し返却を制限したか。未取得はnull |

行の`status=not_present`は、既存のID辞書を読めたが該当IDがないことを表します。破棄済み・非active・別親・型違い・重複したコンポーネントは、正常な空表示へ置き換えません。一部だけ安全に取れた場合はpartialまたはunavailableとし、生値を主一覧の分類へ流用しません。

既存画面が一意で、その画面の実績コンテナ配下にある正確なウィジェットだけを読みます。ツールチップは1行8文字列、各1024 UTF-16単位、1要求の文字列合計8192 UTF-16単位までです。有効なサロゲートペアを途中で切りません。上限に達して返却文字列が[]になっても、既知の元件数とtruncatedを残し、未取得と区別します。

通常UIの表示番号と保存済みツールチップを読むだけで、画面生成・表示・展開・フィルター更新・ツールチップ再構築・要求評価は呼びません。`LocText.text`も、内部のdirty状態を更新する場合があるため使用しません。名前から現コロニーとの一致を推測する処理もありません。画面は過去のコロニーや演出途中の情報を保持し得るため、画面観測を現在の実績フラグや要求別の新鮮な進捗に置き換えないでください。

実際に概要画面を開く場合は、既存の明示操作 `building_control domain=side_surface surface=facility kind=telepad action=open_colony_summary confirm=true` を別途使います。この通常UI操作による要求評価・通知待ち一覧の消費などと、その後の受動読取の効果を分離します。

関連する7つの独自案内・エラーは、PO4ファイルの `OniMcp.MCP.ACHIEVEMENT_READ.*` と、現在のruntime JSON3ファイルの `achievement_read.*` に対応します。中国語runtimeの既存`zh-Hans`と暫定PO名`zh-hant.po`の扱いは変えません。

## 製造ポッドの勝利条件

製造ポッドの一覧で `includeVictory=true`（既定）とした際の `victoryConditions` も、同じキャッシュ読取を使用します。各項目は次の情報を返します。

| 項目 | 意味 |
| --- | --- |
| `id`／`name` | 既存の勝利条件定義のIDと名称 |
| `success`／`failed` | 勝利条件全体のキャッシュ済みフラグ。対応記録がなければ `null` |
| `status` | 一覧と同じキャッシュ状態の分類 |
| `source` | `SaveGame.ColonyAchievementTracker.achievements` |
| `stateMode` | `cached_no_reevaluation` |
| `requirements` | 要求型と、未評価であることを示す情報 |

ここでの `success` は勝利条件全体のキャッシュ済みフラグであり、今回の読取で全要求を調べた結果ではありません。全体の達成フラグを各要求の成功値としてコピーしません。

定義の一覧自体を取得できない場合、`victoryConditions` は `null` です。定義を取得でき、対象となる勝利条件がない場合は `[]` です。定義はあるがトラッカーや対応記録が欠けている場合は、定義の項目を残し、全体フラグを `null`、状態を `unknown` にします。

## 要求の未評価・未取得

通常の要求では、実績一覧のfull取得は `type` と次の値を返します。

```json
{"progress": null, "progressState": "not_evaluated_readonly"}
```

勝利条件の要求には、さらに次の値を含めます。

```json
{"success": null, "successState": "not_evaluated_readonly"}
```

`not_evaluated_readonly` は、要求の実体と型は取得できたものの、読取のための評価を実行していないことを意味します。失敗・進捗ゼロ・達成済みのいずれも表しません。

要求一覧の欠測と、取得済みの空一覧も区別します。

| 取得状態 | 返却 |
| --- | --- |
| 定義の要求一覧が未取得 | `requirements=null` |
| 取得済みで要求が0件 | `requirements=[]` |
| 一覧内の要求要素が `null` | `type=null`、`progress=null`、`progressState=unavailable` |
| 勝利条件の要求要素が `null` | 上記に加え `success=null`、`successState=unavailable` |

本体の要求基底には、要求別の評価結果を汎用的に読み出せるキャッシュ契約がありません。個別の内部値があっても、初期値と実際の評価結果を区別できない場合があります。その値を正常な進捗として扱ったり、進捗取得のために評価メソッドを呼んだりしません。

## 読取が実行しない処理

定義の取得は、既存の `Db._Instance` フィールドを型・宣言元・static属性まで確認して読み取ります。フィールドの解決・読取に失敗した場合や、データベースがまだ存在しない場合に、`Db.Get()` による初期化へ切り替えません。実績一覧は既存のデータ未初期化エラーを返し、勝利条件一覧は `null` を返します。

要求の `Success`／`Fail`／`GetProgress`、実績の `UpdateAchievement`／`IsAchievementUnlocked`／`CheckAchievements` は呼びません。読取用の実績状態・定義・UIを新規生成せず、実績解除・通知消費・条件更新も要求しません。既に読み出した定義とキャッシュだけを投影します。

この制限は、名前に「取得」が付くメソッドでも内部更新を伴う場合があるためです。要求評価によって日報の不足項目が追加されたり、内部進捗が更新されたりする経路を、読取の代用として使用しません。

## 鮮度と検証の境界

キャッシュの最終評価時刻は不明です。`observedCycle` は読取時のサイクルであり、条件を最後に評価した時刻ではありません。`cached_no_reevaluation` はMCPの読取経路を示すもので、ゲーム本体の通常更新まで停止するという意味ではありません。

ゲームの実績画面を開く処理は、通知待ち一覧の消費や要求進捗の評価を伴います。画面との比較は、読取要求が状態を更新しないことの確認とは別の操作・試験として扱います。

この契約は、実機での全項目照合を完了したという主張ではありません。達成・失敗・欠測の代表例、DLCとセーブの適合性、両フラグが同時にtrueになる実機例や演出後を含む画面表示、要求別進捗の安全な取得方法は、引き続き確認対象です。DLCの切替や新たな要求評価経路は、この変更の対象に含めません。

## 先行するキャッシュ読取修正の限定検証

製品の施設・実績読取ソースを直接使うホスト回帰で、評価・初期化・UI呼出しを禁止する514条件を確認しました。旧施設読取コードを使った開発側の負対照では、コンパイル後の要求評価呼出しを検出しました。欠測と既知0件、null要求要素、全体フラグの優先順位などの境界はホストの確認です。

開発版・公開版それぞれの本体参照ビルドと、自前DLL・専用識別子による停止実機の読取を確認しました。主一覧、full既定件数、状態絞込、勝利条件の全体フラグとの対応、要求別の未評価null、その他の製造ポッド項目と反復結果を照合し、時刻・停止・速度を保持しました。保存・シミュレーション進行・実績画面の操作は要求していません。試験後は元の導入物・設定・保存先・既存画像と未起動状態への復帰を確認しました。

評価呼出しを除いた根拠はソースとホストの禁止センチネルです。実機では本体の通常render評価を計測・無効化していないため、ゲーム全体で評価が一度も起きなかったという証明ではありません。ゲーム画面との全面比較、全実機欠測パターン、DLC適合性と要求別の実進捗は未完です。

## 達成・失敗の両フラグがtrueの場合

本体の同期画面処理は、実績・進捗表示の適用後に `failed` を確認して失敗表示を適用します。キャッシュの二つのフラグは独立しており、両方がtrueの記録を読取側で排除しません。一覧と勝利条件の共通分類を失敗優先へ揃え、従来の成功優先で失敗絞込から漏れる場合を修正しました。他の組合せと生のフラグ、未評価の要求情報は維持します。

実ソースを使うホスト回帰550条件で、両方trueの勝利条件・brief/full・件数・状態絞込と生値保持を確認しました。正確な旧実績読取ソースへの差替え対照は、コンパイル後に新しい失敗優先条件で失敗します。これはゲーム内で両方trueの記録を自然再現した証明ではありません。

新規達成の演出は、遅延処理で達成表示を後から適用する場合があります。そのため、この分類を全瞬間の画面状態や演出後の最終表示と同一視しません。通常UIを開く操作とキャッシュの受動読取も分離したままです。

分類変更後も、開発版・公開版それぞれ自身のDLLと専用IDで、停止中の主一覧・full・状態絞込・勝利条件・反復と、時刻／停止／速度の保持を確認しました。観測した実績には両フラグtrueの記録がなく、その境界はソース・ホストの確認に限定します。実績画面の操作や条件評価、保存、シミュレーション進行は要求していません。通常終了後に元の導入物・設定・保存先・既存画像と未起動状態へ復帰しました。

## 任意UIキャッシュ取得の限定検証

実績・勝利条件の既存550条件を保持し、実際の任意UI observerと主一覧を通す追加593条件を確認しました。画面なし／閉鎖／一意性／別親／非active／型・コンポーネント重複／部分取得、既知0件と欠測、検索とlimit、文字数上限とサロゲートペア境界を含みます。旧主一覧全文へ差し替えた負対照はコンパイル成功後、任意UI項目の欠落を検出します。実際のfactoryによる任意booleanと7キーの3言語解決、PO4／runtime JSON3の対応も確認しました。

開発版・公開版それぞれ自身のDLL・識別子で、停止実機の47件と表示キャッシュを照合しました。既定／明示OFFの一致、閉画面のunavailable、明示的な通常UI表示後の全返却ID照合・詳細既定10件・検索後1件・0件・反復、通常UIで閉じた後のunavailableを確認しています。要求の未評価nullと時刻・停止・速度を保持し、保存やシミュレーション進行は要求していません。通常UIを開く操作による評価・通知消費は、受動readの外側で記録しています。

観測した代表例では、失敗と未達成の画面番号と先頭ツールチップ文が同じでした。この表示から状態を推定しないことを維持します。生の画面キャッシュであり、ピクセル照合や現在のコロニーとの自動同定、全欠測パターン・DLC適合性・要求別進捗の確認を完了したものではありません。元の導入物・設定・保存先・既存画像と未起動状態への復帰も確認しました。公開版の実際のtools/listでも、新しい引数が任意booleanで、説明がruntimeカタログへ解決されることを確認しました。
