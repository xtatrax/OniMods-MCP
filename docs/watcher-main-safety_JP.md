# 生存監視の主処理と対象セーブの安全性

`survival_watch.py` の主処理を、現在の MCP 公開経路と対象確認の契約へ揃える限定修正です。既に受入済みの[終了時停止確認](watcher-stop-verification_JP.md)を維持し、過去の意図しない再開原因や native の遅延適用追跡とは分けます。

対象コードは次の二つです。

- [survival_watch.py](../.agents/skills/oni-mcp-autonomous-iteration/scripts/survival_watch.py): 接続、対象確認、監視ループ、終了処理。
- [survival_watch_runtime.py](../.agents/skills/oni-mcp-autonomous-iteration/scripts/survival_watch_runtime.py): RPC/MCP応答、主Content、ops子結果、snapshotと保存先の検証。

## 主処理の要求と応答

主処理のツール要求にも `task` を付けます。作業説明を欠いた旧要求が拒否されたのに、空の結果や既定値を成功と解釈して監視を続けないためです。

通信層、JSON-RPC、MCP の成功、さらに用途別の本文を別々に検証します。

- 空の応答、RPCの `error`、MCPの `isError`、取得不能な主Contentを成功にしません。
- 主結果は `content[0]` の非空のtextとして読みます。供給便方針やmiddleware通知など、後続Contentを主結果の代わりに採用しません。
- JSONとSSEの本文を区別して解釈し、JSONの不正な定数を拒否します。snapshotで必要な時計・停止状態・速度・住民数・警告等も、数値の有限性や型を検証します。
- 不明な停止状態や欠測した指標を、`false`・`0`・正常という意味へ補いません。主処理の失敗は終了時停止処理の結果で消しません。
- 現行snapshotの `green`・`info`・`yellow`・`red` を区別し、`red` では進行しません。未知の色や不完全な診断行も拒否します。`--ignore-critical-diagnostics` は診断要求を省く指定で、snapshotの危険度を無効化しません。

これは要求が実行されなかったことや、通信失敗中のゲーム停止を保証するものではありません。通信成功と本体側の適用・停止確認は別の根拠です。

## 既定公開ツールからのコロニー読取

既定の7ツールの公開surfaceで接続したまま、既存の `world_editor` 窓口を使います。通常のサーバーバッチは内部の `colony_control` を公開ツールとして解決しないため、監視から直接またはバッチで呼べることを前提にしません。

- 最小snapshotは `command=read path=/active/colony/status.oni profile=minimal` から取得します。
- 診断警告は `/active/ops/colony.md` の既存SEARCH/REPLACE経路へ、固定した一行 `call domain=diagnostic action=alerts limit=20 detail=true` を渡します。外側の `confirm=true`・`dryRun=false` は、この固定された読取コマンドだけを実行するための指定です。任意の操作やDSLを入力する窓口へ拡張しません。

診断の結果は、外側の編集結果、内側のops実行結果、`colony_control` の詳細結果を順に検証します。一編集・一コマンドで成功し、予行でも部分成功でもないことを確認し、内側のJSON配列を読んでから診断として使います。`applied` は階層ごとに単位が異なるため、legacyの0を未実行と決め付けず、`executedCommands` と子の成功・実データで判断します。

返す情報は監視に必要な最小snapshotと診断です。内部操作の公開範囲やMODの本体処理は増やしていません。

## 対象セーブの一致と初期ロード

監視の対象は保存先で結び付けます。`--expected-save` で期待する保存先を指定でき、`--no-load` を使う場合はその明示が必要です。保存先は実行環境で指定し、この文書には個別の値を置きません。

1. `game_control domain=launch action=status` で初期状態を読む。
2. 既にゲーム内なら、現在の保存先が対象と一致し、利用可能であることを確認する。不一致を別セーブへの強制ロードで解決しない。
3. 明確に未ロードで、対象を解決でき、通常のロード窓口が利用可能な場合だけ、一度の `action=start confirm=true resume=false` を要求する。
4. 要求後は状態を読み、対象のロード完了を確認する。状態不明、要求失敗、タイムアウトを理由にロード要求を再送しない。
5. 進行を始める前と監視ループ、終了時停止の前に対象を再確認する。

`--no-load` は、現在読み込まれた期待セーブを使う指定です。未ロードならロードへ切り替えず失敗します。初期化の有無が不明な場合も、未ロードと推測して開始要求を送りません。

保存先の照合と速度・停止要求は別のRPCです。照合直後に別クライアントがセーブを切り替える競合まで、サーバー側で原子的に防止する実装ではありません。

保存先の比較は監視対象の取り違えを防ぐ契約です。ファイル内容の同一性やロード前後の状態維持まで、保存先文字列だけから保証するものではありません。

## 開始前の停止と目標ゼロ

初期状態が明確な停止でなければ、既存の `pause_and_verify` で確認します。停止が確定しない場合やincidentがある場合は監視を始めません。最初のsnapshotも停止状態を要求します。

`--target-cycles 0` は、進行を始めずに現在の対象と読取経路を検証する用途です。目標到達を再開より先に判定し、`set_speed` を送りません。開始時に動作中なら停止確認は行い得るため、「全ての状態変更をしない」指定とは異なります。

診断やsnapshotに失敗した場合も、進行を始める理由にしません。目標未到達で進行する場合にだけ、開始条件を確認して速度を設定します。

## MOD不一致通知と終了処理

進行前にはMOD不一致ダイアログの状態を読みます。通知がある、または通知の有無を判定できない場合は再開を拒否します。この監視は通知本文を見て自動的に `acknowledge` を実行せず、通知のOKも代行しません。通知確認の操作契約は[別の窓口](mod-mismatch-dialog_JP.md)を参照してください。

初期停止確認が失敗した場合は、その結果とincidentを保持して終了し、finallyから同じ停止確認を重ねて回数上限を超えません。

終了処理でも対象の保存先を再確認します。対象を確定できない場合、別のゲームを推測して停止操作を送らず、停止状態をunknown・incidentとして報告します。

対象を確認できた場合は既存の停止ヘルパーを使用します。

- 通常pauseの応答後に独立したtimeを読む。
- 停止の `true`・`false`・`null` と有限の時計を区別する。
- 成功応答後も停止がfalseまたは不明なら、同じ入口での再停止は最大一回にとどめる。
- 回復してもincidentを消さず、監視を失敗終了する。通信・RPC/MCPエラーでは再送しない。
- 明示的な `--no-pause-at-end` は維持する。その場合は停止成功を主張しない。

終了時の停止成功だけで、監視中の連続した安全性を証明しません。目標未達、主処理の失敗、停止確認のincidentはそれぞれ保持します。

## 時間制限と残る追跡範囲

`--max-seconds` は初期接続・対象確認・初回snapshotの後に設け、監視ループの要求の合間に確認する実時間の上限です。HTTPのtimeoutもクライアント側の待機期限であり、native操作の適用期限や強制停止期限ではありません。要求処理や終了時確認の待機によって、監視の所要時間は指定値を超え得ます。

クライアントのtimeoutは、受理済みの要求がゲーム側で後から適用されないことを保証しません。今回、通信断中にも働く本体側watchdogや、経過時間による自動停止は追加しません。

過去の停止点検中の時刻差について、UI、別クライアント、遅延処理のどれが再開したかは未確定です。今回の修正から過去の原因を確定せず、native適用時刻と出所の追跡は残作業として扱います。終了時停止ヘルパーの既存受入と今回の主処理受入を合わせても、親TODO02全体の完了にはしません。

### 開発IDのcold拒否とwarm成功

cold状態の主処理では、明示的に未ロードであることを確認してから `resume=false` の通常ロードを一回だけ要求しました。初回snapshotは食料キャッシュの未取得に伴う `red` を返し、主処理は進行せず拒否し、終了時停止を確認しました。このcold側の拒否確認を、warm状態での正常監視成功とは分けます。

初期化後の受入は、別途短い通常進行を行って食料キャッシュが更新され、snapshotが `green` となった状態で実施しました。監視自身が読取値を得るために自動進行した結果ではなく、coldの `red` を無視して続行させる変更も加えていません。初期化直後の診断と確定状態を区別する課題は、今回の主処理修正で完了したものとしません。

warm状態では次の主処理が成功しました。

- 目標ゼロは終了0、sample一件、速度変更なし、終了時の停止確認一回でした。
- 短い通常監視と診断を有効にした短い監視は、それぞれ終了0、sample三件、速度変更一回でした。どちらも最終停止は `confirmed`、incidentはfalseでした。実時間上限で `partialAllowed=true` として終えた限定試験で、指定サイクル到達の成功ではありません。
- 保存先不一致は読取一回で拒否され、ゲーム状態を変更しませんでした。メニューでの `--no-load` もロードや速度・停止操作へ切り替わらず拒否されました。

試験のために原本セーブを保存していません。原本保存をしなかったことと、導入物・設定を含む元環境への復元完了は別の確認です。

公開版でも、目標ゼロは速度変更なし・sample一件、限定監視と診断付き監視は速度変更一回・sample三件で、最後の停止はconfirmed・incident=falseでした。二つの限定進行は実時間上限によるpartialAllowedで、指定サイクル到達の受入ではありません。未ロードと保存先不一致では速度変更・代替ロードをせず、明示的な通常ロードはresume=falseで一回でした。
