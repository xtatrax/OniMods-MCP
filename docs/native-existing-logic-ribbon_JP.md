# 既存リボン線の接続専用操作

同じ定義・素材の完成済みリボン線二セルを、`connect_existing` の `type=logic` で扱う。既存の共有設備分類は変更せず、接続専用の判定だけが本体の正確な `LogicRibbonConfig.ID` を追加で許可する。通常の自動接続・新規敷設・研究回避の対象は広げない。

## 維持する境界

隣接一辺、同一BuildingDef・素材・manager、完成実体と主レイヤー・TileLayerの同一性、置換予約なし、アクティブワールド・可視性・停止・confirmの条件を維持する。通常自動化線との混在、異素材、ブリッジ、移動チューブ、名前が似た別設備は、この追加許可の対象外である。

本体の通常UtilityBuildToolへ、元の定義と素材で二セルだけのドラッグを渡す。新しい設備を置かず、MODから接続マスクやネットワークを書き換えず、失敗時の直接補修・fallback・自動再試行をしない。本体受付、両端の指定辺と同ID・素材の保持、実信号の伝達を区別する。

`connectionVerified` はcallerが本体の合成接続キャッシュを後確認した結果であり、4bit信号伝達の証明ではない。`flowVerified=false` を維持する。予行は本体UIを起動せず、coordinate ops外側の構文予行と子ハンドラーの対象検査も区別する。既存の[接続契約](native-existing-connection_JP.md)は、この限定追加以外を維持する。

## 根拠とホスト受入

インストール済み本体を静的確認した。LogicRibbonは通常LogicWireと同じBaseLogicWireConfigを使い、LogicWire／LogicWireTile／ReplacementLogicWire、1×1、Logic接続のグラフ、FourBit設定を持つ。本体BaseUtilityBuildToolは同定義・同素材の既存実体を再利用し、定義か素材が違う場合には交換予約を作り得る。このため混在のガードは緩めない。

本番caller／native adapter全体に加え、既存分類二メソッドとその比較依存を実ソースからbyte単位で連結した。既存切断69条件・接続253条件を保持し、リボン線47条件を確認した。修正前のcaller全文も同じ試験へコンパイルでき、リボン線受付の実行時assertで失敗する。ホストの本体・Unity境界は代替であり、実機受入ではない。

## 両IDの限定実機受入

開発IDと公開固有IDのそれぞれで、ソース連結369ホスト条件・関連静的検査とゲームDLL参照ビルド（警告0・エラー0）を確認し、別々の試験分岐で通常UIの接続専用経路を実機照合した。公開側は固有のDLL・設定・識別子と読込版を照合した。4セルの完成リボンの中央一辺を切断すると、別の設定読取経路でリーダーの入力8/出力1が0/0へ変化し、再接続で8/1へ復帰した。選択bitの設定読取だけを信号伝達の証明にしていない。短時間の通常進行と停止後、通常保存再読込後にも同じ信号を確認した。

全可視の周辺27セルで実体集合・地形・予約、11実体のID・素材・質量、リボン外側二辺、同居電線を照合した。物理方向はセルMarkdownのnative physical接続の表示を使い、隣接存在から作るconnectionSummary/nearby_ports.lineは根拠にしない。接続callerのvisual/physical合成キャッシュと物理mask全体の同一性も仮定しない。再要求は追加ジェスチャー0、通常自動化線との混在は拒否された。保存再読込で一覧順は変わるため、同じ実体の集合として比較した。

両IDで通常保存再読込を確認した後、元セーブの停止ロード・選択先、控えた導入物・設定・原本・共有保存領域と開始時のゲーム未起動状態への復帰を独立照合した。共有保存領域は今回最初のnative保存前に控え、新規・更新データは別途保全した。prefsは元選択先を確認し、通常起動で変わるセッション番号は書き戻していない。

試験設備の準備は許可済みsandboxで行ったもので、新規敷設の通常工事完了・実機全方向・全16信号値を検証したものではない。個別の保存名・座標・実体ID・設定・ログ・開発履歴は公開差分に含めない。

この下位項目だけで、混在端点、太線、他の派生管、移動チューブ、置換中の競合や接続系全体のTODOを完了扱いにしない。
