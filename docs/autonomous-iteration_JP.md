# 自律的な反復作業: 根拠と進行条件

OniMods の保守エージェントと、上流プロジェクトの調査に適用します。既存のプレイ時の安全指示も引き続き適用されます。定期実行は調査する許可であり、コミットを作成する義務ではありません。

## 繰り返しではなく、現在の状態に基づいて作業を選ぶ

- 現在の main、進行中の作業、変更されたファイル、レビュー指摘、および対象の head SHA に対する CI を確認します。過去の会話での報告は調査の手がかりであり、確定した結果ではありません。
- 各役割で実装中の PR は最大1つにします。同じ問題には既存の PR を再利用してください。他の役割が編集中のファイルでは作業しません。
- ONI の実行環境、認証情報、外部の判断が得られないことだけが障害となっている PR は保留にし、繰り返しリベースしません。障害、テストした SHA、必要な根拠、再開条件を、本文または1件の状況コメントに一度記録します。
- 保留中の PR を再確認するのは、新しい根拠、関連ソースの変更、レビュー指摘、実際の競合が生じたときです。それ以外は多くても1日1回にします。main の無関係なファイルが更新されたことは、強制プッシュ、履歴のスカッシュ、CI の再実行の理由にはなりません。
- 保留中の作業がある間は、独立してテスト可能な別の問題に取り組みます。作業待ちの列を進めるためだけに、実行時の受け入れ条件を緩めてはいけません。
- チェックを発火させるための空コミットや無関係な変更を作成しません。他の貢献者のコミットを上書きしません。main への追従は、マージの準備時や実際の依存関係が変わったときに行い、タイマーが動くたびには行いません。
- 意味のある変更がなければ、新しい Issue、PR、繰り返しの状況コメントは作成しません。

## 根拠が示せる範囲を明確にする

すべての主張には、出典、リビジョン、コマンドまたは実行 URL、結果、限界が必要です。

| 根拠 | 確認できること | 確認できないこと |
| --- | --- | --- |
| ソースのパターンに基づく前提条件の検査 | 想定するテキストが存在すること | 実際の動作や性能 |
| ホスト環境での実行テスト | そのホスト環境・テスト条件で動作させた挙動 | Unity/Mono やゲーム状態の正しさ |
| 参照ビルド・API インターフェース | 固定した参照 API との互換性 | より新しいゲームビルドとの互換性 |
| リビジョンを固定した逆コンパイルソースの前提条件 | そのリビジョンにおける、選択したメソッド本体への仮定 | 別のバイナリミラーの出自 |
| 合成ベンチマーク | 明示した合成ワークロードでの処理・メモリ割り当て・時間 | ゲームの FPS や実際の処理頻度 |
| ONI 実行時の記録 | 観測したビルド・セーブデータ・MOD・テストシナリオ | 未検証のビルド、セーブデータ、MOD の組み合わせ |

2026年9月16日の監査時点で、コンパイル用ミラーの `Sgt-Imalas/Sgt_Imalas-Oni-Mods@be4a70d8f335fdd8ac7f3b1ccf91b50bb6ddb46d` は対象ビルドを **737790** としています。別途固定されているソースの前提条件では **744825** としています。常に現在のマニフェストを確認してください。ソースのタイムスタンプや公式のリリース番号によって、そのミラーのバイナリが裏付ける対象ビルドが新しくなるわけではありません。

変更不能な上流リビジョンへの固定は、再現性の基準であり、更新検出の仕組みではありません。同じ固定コミットをダウンロードするジョブでは、上流の main の変更を検出できません。調査では上流のリビジョンを別途比較し、レビューを経る固定先の更新を提案する必要があります。ハッシュや基準値を黙って更新しないでください。

ダウンロードしたゲームアセンブリと逆コンパイルした実装ソースは、一時的にだけ保持します。アセンブリはコンパイルと静的なメタデータの確認にのみ使用し、第三者のゲームバイナリは実行しません。検証後にアップロードしてよいのは、許可リストに含まれるシグネチャやレポートだけです。生のソース、DLL、認証情報、非公開のセーブデータはアップロードしません。

## テストは動作の変化を検出するものにする

アサーションごとに新しい実行プロジェクトを作るより、関連する既存のテストプロジェクトを拡張します。回帰テストは既知の不具合がある動作では失敗し、修正後に成功する必要があります。grep 用マーカーや対応表の JSON は補助的な根拠であり、公式の適合性テストを実行したことにはなりません。

PR またはプッシュの全範囲に対して、実際に `git diff --check` を実行します。`Mod quality` ワークフローは、負荷の高いテストより前にこのチェックを行います。ローカルで GitHub の DNS を利用できない場合は、完了した CI の該当ステップを根拠として示してください。ローカルにチェックアウトできたと主張したり、再構成した抜粋を完全な差分と混同したりしてはいけません。履歴が不足している場合は失敗であり、正常なスキップではありません。

行数制限を満たすためだけに、コードを詰め込む、有用なコメントを削除する、複数の文をまとめるといったことはしません。責任範囲を分割するのは、読みやすさが向上する場合だけです。既存のテスト、ベンチマークのしきい値、セキュリティ上の条件を弱めないでください。

性能改善では、まず正しさを修正します。基準と変更後のリビジョン、実行環境、ワークロード、ウォームアップ、サンプルの順序、メモリ割り当て、ばらつきを記録します。結果を見る前に成功基準を決めてください。ホストされた単一ランナーのノイズに合わせて、しきい値を上げ続けたり分類条件を追加したりしないでください。可能な場合は、楽観的な別モデルを維持するのではなく、本番の補助処理を測定します。

既定で無効な計測機能でも、実行タイミング、ライフサイクル、並行処理、観測そのものの負荷をレビューする必要があります。計測用だからといって、自動的に低リスクになるわけではありません。

## マージと引き継ぎ

- 差分全体と、関連する呼び出し元、テスト、失敗時の処理を読みます。レビュー枠を使い切った場合は、独立したレビューが行われていないという意味であり、承認ではありません。
- 必須チェックを、正確な候補 SHA に対して確認します。待機中、スキップ、キャンセル、対応が必要、未実行のチェックは成功ではありません。以前の SHA に対するチェックは、現在の候補の根拠になりません。
- ゲームプレイへの書き込み、セーブ・ロード、ライフサイクルの変更、安全性が保証できないパッチ同士の相互作用については、実行時の検証条件を維持します。ゲームを実行していなければ、実機検証済みとは主張しません。
- スカッシュマージの前に head・base とレビュー状況を再確認します。リポジトリの保護設定を回避しません。main に強制プッシュしません。
- マージ SHA を記録し、main の CI を確認します。プッシュ後の CI が保留中なら、保留中と報告します。次の反復作業では、他の作業を始める前にその結果を確認します。
- 永続的に記録するのは重要な判断だけです。可能なら、目印付きの状況コメント（`<!-- onimods:iteration-state -->`）を1件再利用します。ボットの要約を再帰的に包み込んだり、状態が変わらない確認のたびにコメントを増やしたりしません。

プロジェクト横断の上流調査は radar の役割です。実装担当は、担当作業に関係する上流の変更だけを確認します。共通 CI や参照設定の編集は、ユーザーによる直接の監査で調整されている場合を除き、API/CI 担当が受け持ちます。

報告は簡潔にし、実際の変更、検証の水準、Issue・PR、障害を示します。変化のない上流バージョンを繰り返し報告したり、利用できない実行環境での検証を約束したりしません。根拠のない活動を増やすより、何もせず静かに終えるほうが適切です。
