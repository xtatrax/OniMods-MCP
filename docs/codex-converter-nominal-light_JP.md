# 図鑑の変換パネルから、照明の定義値を限定取得する

既存のデータベース本文読取で、選択した正確な本体型の `CodexConversionPanel` に `converterNominalLight` を添える。パネルが保持する現物と、読み込み済みPrefabキャッシュの参照が同一だと確認できる場合だけ、既存の正確な本体型 `Light2D` の `Lux` と `Range` を読む。新しいAPI、ゲーム操作、照度計算は追加しない。

## 返却する値の意味

照明部品まで確認できた場合、次の項目を返す。

| 項目 | 意味 |
| --- | --- |
| `available` | 照度を観測でき、範囲も有限値として観測できたか |
| `status` | 両方を観測した `observed`、片方だけの `partial`、どちらも未取得の `unavailable` |
| `source` | `CodexConversionPanel.Converter/Assets.TryGetPrefab/Light2D.Lux/Range` |
| `semantics` | `nominal_cached_prefab_light` |
| `lux` | `available`、`status`、観測した整数または `null` の `value`、`unit=lux` |
| `range` | `available`、`status`、観測した有限値または `null` の `value`、`unit=cells`、`semantics=radius` |

`Range` はセル／タイルを単位とする定義上の半径で、直径や実際に照らされたセル数ではない。`Lux` も既存部品が持つ定義値であり、複数光源の合成、距離減衰、遮蔽、実行中の点灯状態を評価したセル照度ではない。

`available` は必要な値を観測できたかを示し、物理的に妥当、稼働中、安全な照明という判定ではない。既知の0はそのまま返す。有限の負値も補正せず保持するが、値が有限なことを有効な照明設定と保証しない。未取得を0や本体の初期値で埋めない。

照度と範囲は独立して読む。一方の取得に失敗しても、他方の観測値を残す。範囲が非数値または無限大の場合は、その `value` を `null`、`status` を `invalid_numeric` にする。読み取れない場合は `read_unavailable` とする。いずれも他方の既知値を消さず、補間や換算をしない。

## 欠測、部品なし、識別不能

照明部品の取得前に条件が満たされなかった場合は、`available=false` と機械判定用の `status` だけを返す。キャッシュや参照の欠測、参照不一致、型の相違、取得例外から定義値を推測しない。

同一のキャッシュ済みPrefabまで確認でき、照明部品が無かった場合は `not_present` とする。これは照度0の測定値ではない。通常の非照明設備や動物に照明部品がないことだけを、新たなエラー項目として扱わない。正確な本体型の部品まで確認できた後の数値欠測と、それ以前の簡潔な欠測表示は区別する。

パネルに追加項目がない場合も、暗闇や照度0とは判断しない。対象外のパネル、予算不足などでは項目自体が付かない。

## 参照と読取の境界

既存の `Converter` が実際の `GameObject` であること、既存部品が正確な本体型 `KPrefabID` で有効な `PrefabTag` フィールドを持つこと、そのタグの `Assets.TryGetPrefab` が同じ参照を返すことを順に確認する。その後、正確な本体型 `Light2D` の既存部品だけを対象にする。派生型を既知の本体型として扱わない。

`assetName`、同名の別Prefab、同じタグを持つ別のオブジェクトへ切り替えて成功としない。追加項目には、生Prefabのタグや名前を新たに公開しない。従来の生データにある `Converter.assetName` の意味と出力は変更しない。

既存の有効なタグを使う受動キャッシュ照会に留め、対象の生成、タグ登録、警告付きPrefab取得、キャッシュ初期化、UIの `Configure`、記述子の評価、値の設定、照明の更新やシミュレーションは行わない。本体の通常プロパティ／部品アクセスを使うことと、実行環境全体の型初期化や内部処理の時機を停止する保証は別である。

既存の本文選択、DLC、ロックの確認を保ち、選択していない本文や全Prefabを走査しない。フォーマッターは引き続き実行せず、`callbackPresent`、`formatter_not_executed`、`renderedUiComplete=false` の境界を変えない。

## 共有予算と長文取得

小さな追加オブジェクトのため、既存パネルの共有ノード予算から20ノードを先に予約する。不足する場合は追加項目を丸ごと省き、既存の `data_limit` を保持して、部品やPrefabキャッシュを照会しない。

この予約は、そのパネルの生フィールドの読取が済んだ後に行う。生値を遡って計算・補正したり、既に読んだ内容を削除したりしない。共有ノード予算は出力投影の範囲を制御するもので、本体APIの実行時間や全メモリ確保を制限する保証ではない。文字数制限、長文ページング、再読時の改訂確認は従来どおりで、追加項目による本文量の変化もその対象になる。

## 検証の区分と残る範囲

開発版・公開版それぞれで、実ソースをリンクしたホスト回帰と本体DLLを参照するビルドが成功した。直前のカテゴリ・昇華・捕食対応済み読取ソースの全文を使う負例は、コンパイル成功後に従来の回帰を通過し、新しい照明定義値の検査で失敗した。既知0、有限の負値、非有限な範囲、独立した取得例外、キャッシュ参照不一致、欠測、派生型、部品なし、DLC／ロック、共有予算はホストで確認した範囲であり、本体で異常状態を再現した証拠とは扱わない。

両版それぞれの停止した実機で、親の `LIGHTBUGSPECIES` の既存本文から `LightBug` と `Phosphorite` の変換パネルを読み、照度と半径の定義値、単位、観測状態、由来を確認した。初期値で補う経路を追加したのではなく、選択済みパネルの現物とキャッシュの同一参照を確認する経路による取得である。通常照会の反復と、長文ページを連結した本文で、生フィールドと追加の定義値が一致した。

非照明の対照として、`Raptor` の `Hatch` 入力と `Meat` 入力のパネルは `not_present` を返した。`Hatch` の生の数量・`continuous`・`callbackPresent` と既知の捕食単位メタデータを保ち、`Meat` の生の数量、`customFormating=null` と `amountSemantics` がない状態も保持した。この対照の取得を、実際の捕食や消費速度の測定とは扱わない。

照明親本文の通常照会は文字数で打ち切られ、長文ページの連結後は文字数による打切りが無くなった。一方、未対応画像が残るため、通常照会と連結後の双方で `complete=false` のままである。定義値の `available=true` やページ連結の成功を、全本文の意味解釈、全画像、描画UIの完全再現へ一般化しない。読取窓の前後でゲーム内時刻・速度・停止状態・対象セーブを維持し、その読取では進行・保存・UI構築・キャッシュ初期化・照明更新・シミュレーション・フォーマッター呼出しを要求していない。

両版はそれぞれの配備物による独立した読取窓で確認しており、開発版の実行証拠を公開版の代用にしていない。実際の点灯、セルごとの照度・遮蔽・減衰、全設備／全動物／全DLC／他MODの型、描画UIの完全再現は対象外である。放射線、未分類の関数、植物や他の単位、画像等の不足も、この追加によって解決したとは扱わない。親TODOは未完了のまま保つ。

## 試験後の復帰

両版の限定読取後、元セーブを停止状態で選び直し、通常終了を経て元の導入物とMOD設定へ戻した。記録した導入物・設定、保護セーブ、主保存先・共有保存先・既存画像、本体DLLと非対象MODの保持を照合し、開始時と同じ未起動状態を確認した。本体の通常ロード・終了で保存された選択先や採番値を照合し、設定ファイルへ直接書き戻していない。
