# 捕食量の単位の意味を、既知の本体フォーマッターから示す

既存のデータベース本文読取で、正確な本体型の `ElementUsage` が特定の捕食用フォーマッターを持つ場合だけ、`amountSemantics` を添える。新しいAPI、数値計算、ゲーム操作は追加しない。

## 返却項目

追加するのは次の関数メタデータだけである。

```json
"amountSemantics": {
  "rawUnit": "entity_count_per_second",
  "nativeDisplayUnit": "entity_count_per_cycle",
  "source": "GameUtil.GetFormattedPreyConsumptionValuePerCycle",
  "formatterExecuted": false
}
```

`rawUnit` は、既知の本体関数が受け取る数量の意味で、秒あたりの個体数を示す。`nativeDisplayUnit` は、その関数が本体の表示でサイクルあたりの個体数として整形することを、一次ソースから示す。実際に整形した表示文字列、サイクル換算済みの数量、観測した摂食量は返さない。

通常の予算内では、`tag`・`amount`・`continuous`・`customFormating.callbackPresent` の生値を補正せず保持する。既存の0や負値も変更しない。単位メタデータは数値の妥当性や利用可能性を示すものではなく、新しい有限値検査、補正、流量・摂食予測は追加しない。入力側の関数から、産出物や他の行の単位を推測しない。

**`amountSemantics` が無い項目をkg/sと決めつけない。** 未分類の関数、関数なし、予算不足などで項目が付かない。既存の `tag`・`amount`・`continuous` と不足表示を併せて読み、不明な単位を補わない。

## 識別条件と未実行の境界

対象は `Func<Tag,float,bool,string>` の関数が、本体の単一の静的メソッド `GameUtil.GetFormattedPreyConsumptionValuePerCycle` とデリゲートの等価比較で一致する場合だけである。名前だけで判定せず、異なる宣言元・インスタンス・ラッパー・複数呼出しのデリゲートは分類しない。植物を直接食べる関数や植物の保管物を食べる関数、未知の関数、`null` も対象外である。

関数を呼び出して意味を調べることはせず、`GetInvocationList` による列挙も追加しない。既知と判定できた場合も `customFormating` は `callbackPresent` のまま、`formatter_not_executed` と `renderedUiComplete=false` を保つ。単位の意味が判明したことを、表示コールバックや画面全体の実行・再現成功とは扱わない。

識別には標準の静的メソッド参照を使い、追加コードは本体の静的フィールドを読まない。本体関数の呼出しと、実行環境が型をロード・初期化する時機は別であり、実行環境全体の型初期化を停止する保証はしない。`formatterExecuted=false` は、この読取が当該フォーマッター本体を呼ばないという境界である。

## 共有予算

追加の小さなオブジェクトを付ける前に、既存パネルの共有ノード予算から5ノードを予約する。不足すれば `amountSemantics` を追加せず、`data_limit` を `issues` に保持する。

同じ共有予算を使うため、この追加により後続の生データも予算境界で打ち切られる可能性がある。全ての境界で旧出力と生データ全体のバイト列が同一だとは保証しない。通常の予算内の値を計算・補正しないことと、予算上限での取得範囲は分けて扱う。文字数の制限や長文ページングも従来どおり適用される。

## 既存の親本文を読む経路

本体の一次ソースでは、生成済みの子項目の本文を、親項目の `contentContainers` へまとめている。開発版・公開版それぞれの実機で、親の `RAPTORSPECIES` の既存本文から `Raptor` の捕食用パネルを取得した。この読取ではグローバルな子項目テーブルと `RAPTOR` の個別メタデータ照会は空だったが、親本文には対象の生成済み内容が含まれていた。子IDの照会で見つからないことを、子の定義そのものが存在しない証拠とは扱わない。

この追加は既存キャッシュの読取に留まり、Codex初期化、子IDの登録、UIの `Configure`、対象の生成、食性の再計算を行わない。子IDの照会が見つからない場合に親へ勝手に切り替え、成功した子項目の読取として扱うこともない。`CodexReadTools` の取得経路は変更しない。

## 検証の区分と残る範囲

開発版・公開版それぞれで、実ソースをリンクしたホスト回帰と、本体DLLを参照するビルドが成功した。直前のカテゴリ・昇華対応済みパネル読取ソースの全文を使う負例は、コンパイル成功後、既存回帰を通過してから新しい単位メタデータの検査で失敗した。既知／未知／植物／同名の別関数／ラッパー／複数呼出し、既知の0・負値、未実行のカウンター、共有予算はホストで検証した範囲である。

開発版・公開版それぞれの停止した実機で、`Raptor` の `Hatch` 入力の生の数量・`continuous`・`callbackPresent` と、上記の4項目の単位メタデータを確認した。別の `Meat` 入力は生の数量を保持したまま、コールバックも単位メタデータもなかった。`Drecko` の `SpiceVine` 入力は `callbackPresent=true` だが、単位メタデータは付かなかった。この未分類の関数の識別やkg/sなどの単位を、返却内容から推測して補わない。

親本文の通常照会は文字数で打ち切られ、長文ページの連結後は文字数による打切りが無くなった。双方で選択した捕食行の生データと単位メタデータは一致し、通常照会の反復も一致した。一方、未対応画像と未実行コールバックの不足が残るため、どちらも `complete=false` のままである。ページ連結の成功を全本文の意味解釈や描画UIの完全再現へ一般化しない。前後でゲーム内時刻・速度・停止状態・対象セーブを維持し、進行・保存・UI構築・キャッシュ初期化・フォーマッター呼出しは要求していない。

同名の別関数・ラッパー・複数呼出し、0・負値、予算境界などはホストで確認した範囲であり、実機での再現とは扱わない。実際の捕食、サイクル換算した数量、全コールバックの分類や型初期化の時機も確認範囲外である。両版はそれぞれの配備物による独立した読取窓で確認しており、開発版の結果を公開版の実行証拠として代用していない。

対象は既知の捕食用フォーマッターに関する単位の意味だけであり、実際の捕食、全ての食性・植物系の関数、産出物の単位、特殊フォーマッターの実行、照度・放射線や描画UIの完全取得は引き続き別の確認が必要である。[本文取得の契約](codex-read_JP.md)も参照する。

## 試験後の復帰

両版の検証後、元セーブを停止状態で選び直し、通常終了を経て元の導入物とMOD設定へ復帰した。記録した導入物・設定、両方の保護セーブ、主保存先・共有保存先・既存画像、本体DLLと非対象MODの保持を照合し、開始時と同じ未起動状態を確認した。本体が通常ロード・終了で更新する選択先や採番値は、その保存結果を照合し、設定ファイルへ直接書き戻していない。
