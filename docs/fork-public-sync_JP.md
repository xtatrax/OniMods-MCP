# 開発変更を fork_public に反映する手順

通常の実装・試験・文書更新とコミットは `xt-dev-gpt` で行う。`fork_public` は通常開発の作業先にしない。公開可能であるという理由だけで、毎回同じ変更を公開側へコミットする運用は廃止する。

`fork_public` へ反映するのは、次のいずれかに該当する必要な変更だけとする。

- 公開版固有の互換性、識別子分離、プライバシー保護、公開停止ガードの維持。
- 公開版にも存在する不具合の修正。
- 公開版へ採用した変更に不可欠な依存修正。
- ユーザーが公開版への反映を明示した変更。

通常の新機能、実験、開発途中の変更、個別プレイ記録は開発側に留める。選定時には、公開側にも必要な理由と最小限の反映範囲を確認する。開発側の変更はまず `xt-dev-gpt` へコミットし、必要な公開差分だけを以下の手順で別コミットにする。公開版固有の保守は公開側だけで対応してよい。

この手順はバックグラウンド同期や自動pushを導入しない。必要と判断した公開側のローカル反映について毎回許可を取り直す必要はない。リモートへのpush、PR作成、配布、Steam公開は含まない。

## 1. 作業開始時に確認する

- `git status`、現在のブランチ、`git worktree list`、`fork_public` の先端を読み直す。保存済みのパスやSHAを現在値として決めつけない。
- 既存の未コミット変更・他の作業者の変更を保持する。必要なファイルの編集前内容を取得し、必要ならバックアップする。
- `fork_public` が別の作業ツリーで使用されていれば、そこでの状態を確認する。使用中ブランチの参照を別の場所から強制更新しない。
- 公開側の `PUBLIC_RELEASE.md` と `docs/main-differences_JP.md` がある場合は読み、公開版固有の識別・制限・比較基準を維持する。

## 2. 公開可能な差分だけを選ぶ

実装・テスト・一般化した手順や不具合説明は反映する。以下は公開コミットに含めない。

- 個人名・アカウント識別子・個人の連絡先、Cookie、トークン、認証情報。
- 個人の絶対パス、ホスト名、内部IP、固定の配信ルーム、環境固有の設定値。
- セーブ名・個体ID・座標・時刻などを含む個別のプレイ記録、生のMCP応答、スクリーンショット、実機ログ。
- ローカルのクライアント承認設定、定期実行設定、一時スクリプト、バックアップ、ビルド成果物、ゲーム本体のDLLや逆コンパイル実装。
- 個別ワールドへの許可、チャットのやり取り、開発環境だけで有効な常設例外。

説明に必要な値は、環境変数・利用者が入力する設定・架空のテスト値・相対パスへ置き換える。実測値を架空値へ置き換えたものを実機証拠と呼ばない。必要なら検証方法と結果の要約だけを残し、実機ログを含めない旨を示す。

著作権・ライセンス・上流や移植元のクレジット、公開された参照資料、ゲームAPIの定数は保持する。個人情報の除去を理由に必要な出典まで削除しない。

個人用ログだけの変更や通常の開発機能など、公開側に必要な差分がない場合は公開コミットを作らず、完了報告に「公開反映不要」と理由を短く記載する。空コミットは作らない。

## 3. 公開履歴を隔離したまま反映する

- `fork_public` の現在の先端から、確認済みの差分だけを手作業またはパッチとして適用する。開発側の履歴をmerge、rebase、pullで取り込まない。
- 開発コミットをそのままcherry-pickしない。パッチから必要な変更だけを適用し、内容・コミット本文・作者情報を公開用に点検して、新しい公開コミットを作る。
- 開発ツリー全体のコピー、`.git` のコピー、ブランチの作り直し、既存の公開履歴の強制書換えをしない。
- 公開側の `PublicFork.OniMcp` 識別子、設定の分離、Steam公開停止ガード、固定アカウントなしの既定値を保持する。開発用の識別や公開先を上書きしない。
- 公開用に既に削除した設定・ログを復活させない。`.gitignore` は追跡済みファイルやコミット履歴から情報を消さない。
- 公開ブランチだけの変更なら、必要のない開発側への逆反映を行わない。両側に必要な手順書などは、それぞれの既存指示を保ったまま追加する。

公開コミットの作者・コミッターには、リポジトリ全体のGit設定を書き換えず、コマンド単位で次の中立名義を指定する。

```sh
env GIT_AUTHOR_NAME='Public Fork Contributors' \
    GIT_AUTHOR_EMAIL='maintainers@example.invalid' \
    GIT_COMMITTER_NAME='Public Fork Contributors' \
    GIT_COMMITTER_EMAIL='maintainers@example.invalid' \
    git -c commit.gpgsign=false commit -m 'Describe the public change'
```

リポジトリでCLIラッパーの指定がある場合は、その指定に従う。コミット本文に個人用パス・非公開ログ・チャット内容を含めない。上流の必要な帰属表示はソースや文書に保持する。

## 4. 検査して記録する

1. 公開側で実際に適用された差分を読む。内容だけでなく、追加ファイル・画像・リンク・設定・コミットメタデータも確認する。
2. 変更に関係するホスト試験やビルドを実行する。文書だけならリンク・記述・差分の検査を行い、無関係な実機試験は追加しない。
3. 個人・環境情報と秘密情報の残存を検索し、`git diff --cached --check` を通す。ヒットした機密値を報告文や新しい検査ファイルへ転載しない。
4. 明示したファイルだけをコミットする。開発側の未コミット作業を巻き込まない。
5. コミット後にブランチ・差分・作者／コミッター・作業ツリーを確認する。公開履歴の親は直前の公開コミットとし、開発履歴への接続がないことを確認する。
6. 挙動・互換性・公開範囲が変わる場合は `docs/main-differences_JP.md` や関連文書も更新する。固定リビジョンの過去の比較・集計を現在値に見せず、必要に応じて追補または新しい比較対象を明示する。
7. テストの未実施・既存失敗・実機未検証を区別する。開発版の実機確認を公開IDの実機確認済みとして扱わない。

完了報告には、開発側と公開側のコミット、公開対象から除外した情報の種類、実施した検証と残る制限を簡潔に記載する。公開対象なし・競合・権限制限などで反映できない場合も、理由を明示し、両側完了とは報告しない。安全に反映できる部分は先に完了する。

この手順の指示書自体も公開可能な内容を維持し、開発側と公開側で共通に管理する。
