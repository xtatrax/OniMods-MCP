# Harmony registration host regression

The suite links the complete production `ModInfo.cs`, `OwnedHarmonyPatchAudit.cs`, `ServerTools.cs`, `ServerStatusTools.cs`, `SpeedTransitionTracePatch.cs`, `InputSafetyPatchVerifier.cs`, and `AutoDisinfectPolicy.cs`, plus the actual MCP result types and serializer. It runs the real bootstrap, manual Ensure methods, both Db callback invocations, and all three status routing/schema entry points.

```sh
rtk proxy dotnet run --project tests/OniMcp.HarmonyRegistration.Tests/OniMcp.HarmonyRegistration.Tests.csproj
```

The base-class fixture follows the installed game's `UserMod2.OnLoad(Harmony)` shape: it registers attributes by calling `harmony.PatchAll(assembly)` once. A controlled Harmony metadata table represents the linked attributed classes and manual patches. Preparation order, one base call, no extra parameterless PatchAll, subsequent Ensure order, and unchanged registrations after two real Db callback invocations are behavior assertions. The matching-owner value is read from the linked Ensure constants, so development and public variants keep their own identity. Other loader owners or other mods can still add registrations; this change does not repair or promise to eliminate those cases. Overlay/registry/server startup services are substitutes, so their complete initialization semantics are not proven.

Audit cases distinguish legitimate distinct hook methods from repeated identical original/kind/hook identities, including repetitions under different owners. They cover all four kinds, canonical overloaded/generic/array/byref signatures, foreign hook exclusion, owned hooks on foreign originals, deterministic bounded rows with complete global counts, unavailable/null/throwing metadata, and preserved unknown values in serialized status. A throwing `Patch.GetMethod` canary rejects patch-factory execution. The global generic `Tuple` fixture also preserves the installed game's namespace collision for compile checking.

`ModInfoSource`, `PatchAuditSource`, `ServerSourceRoot`, and `PatchSourceRoot` support temporary source-copy overrides for negative acceptance. The prior complete bootstrap and focused behavior-changing mutations must compile before their behavior failures count as detected. The production files are never edited for those runs. The accepted host run passed 14 bootstrap, 174 metadata-audit, and 64 actual status-route assertions (252 total). The previous complete bootstrap and nine mutations compiled and then failed the behavior assertions: early base registration, owner included in grouping, ignored patch kind, unknown count changed to zero, totals computed only from returned rows, patch-factory execution, default-on scanning, string booleans accepted, and foreign hooks included.

Harmony scanning, class processing, metadata, method bindings, and the native base/Unity/PLib/configuration boundaries are fixtures; this does not execute Harmony's native patch engine, Unity lifecycle, all production patch classes, other installed mods, or the game. Tool descriptor DTOs and localization lookup are metadata boundaries here. Real merged assemblies may also contain bundled PLib hook methods under other owners; the PLib shared-registry winner and bundled hook inventory are not modeled, and no full merged-assembly count or single-owner requirement is asserted. Reference compilation against the installed assemblies and actual ONI registration inventories remain separate acceptance evidence. Unknown/racing metadata is not zero normal state, and diagnostics do not remove/reinstall patches.
