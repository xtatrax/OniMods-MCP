# NavGrid のワークロード計測

これは Issue #25 向けの、開発者専用の計測機能です。ONI プロセスの起動時に `CYCLETRIM_NAVGRID_PROBE=1` を指定しない限り無効です。`true` と `yes` も使用できます。変数がなければ Harmony は読み込み時にパッチをスキップするため、通常の CycleTrim ユーザーに呼び出しごとの計測負荷はかかりません。

計測機能は、実際の引数なしの `NavGrid.UpdateGraph()` を範囲拡張の前に観測し、将来の低コストな振り分け処理でも把握できるデータだけを集計します。対象は、ONI が保持する重複のない変更対象セル数、`updateRangeX`、`updateRangeY`、起点セル群の外接矩形における密度です。`UpdateGraph` の置き換え、`DirtyCells` の変更、最適化経路の選択は行いません。

レポートは累積ヒストグラムです。整形とログ出力は `UIScheduler.ScheduleNextFrame` を通して後から行い、`UpdateGraph` の prefix は既存の変更対象セル一覧の走査と、固定サイズのカウンターの更新だけを行います。`UIScheduler` は ONI の時間倍率に影響されない UI クロックを使うため、シミュレーションの実行中に要求されたレポートは、ゲームを一時停止した後でも出力できます。レポートは、呼び出し回数が1、64、256、1024に達したときと、その後4倍になるたびに要求します。通常のレポートは、変更対象セル数・範囲・密度の組み合わせのうち、頻度が高い上位12区分だけを表示し、通常の開発ログを読みやすく保ちます。

定量的な記録には、ONI の起動時に `CYCLETRIM_NAVGRID_PROBE_CAPTURE=1` も指定します。すると、各レポートの出力時点で、上位12区分だけでなく、件数がゼロでないすべてのヒストグラム区分を含む `[CycleTrim][NavGridProbeCapture]` 行を追加出力します。開発ログの1行がかなり長くなる可能性があるため、この完全記録モードは明示的に有効化する方式とし、Issue #25 の根拠を集める間だけ使用してください。

得られた ONI のログは、次のように解析します。

```bash
python scripts/analyze_cycletrim_navgrid_probe.py /path/to/Player.log --pretty > navgrid-capture.json
```

解析ツールは、ログ内の最新の計測開始を使い、`NavGrid.UpdateGraph() resolved` と `target reached; aggregate sampling started` の両方のマーカーを必須とします。FastTrack によって基準状態のサンプリングが無効化された記録は拒否し、全区分の件数の合計が報告された呼び出し回数と完全に一致することを確認します。そのため、上位12区分だけのレポートや途中で切れたレポートは、誤解を招く処理割合を黙って出力せず、失敗します。

条件を管理した計測区間を設けるには、まずログを解析して最新の `calls` の値を記録します。その後、次のレポート出力時点を越えるまで十分に長く対象の処理を実行し、一時停止します。時間倍率の影響を受けない UI スケジューラーが、保留していた完全なレポートを出力するまで待ってから、再度解析します。

```bash
python scripts/analyze_cycletrim_navgrid_probe.py /path/to/Player.log --after-calls 256 --pretty
```

`--after-calls` は、現在の計測実行にある既存の完全記録と一致しなければなりません。比較対象として受け付けるのは、それより後に取得され、累積呼び出し回数が大きい記録だけです。解析ツールは、後の完全ヒストグラムから基準となる完全ヒストグラムを差し引きます。トップレベルの `calls`、`empty`、`buckets`、`candidateGate` は新たな計測区間だけを表し、`baselineCalls` と `cumulativeCalls` は累積値の両端を保持します。各区分のカウンターは単調増加し、その差分の合計が新たな呼び出し回数と完全に一致する必要があります。不正または不整合な区間は、安全側に倒して失敗し、以前の処理分布を黙って使い回すことはありません。

実行時の NavGrid 計測は、依然としてプロセス単位の static な状態で、現在はセーブ・セッションの世代マーカーを持っていません。そのため、`--after-calls` の区間は、同じロード済みゲーム・セッション内に収める必要があります。セーブ・ロードの切り替えより前に基準点を置かないでください。プロセスを再起動すると最新の計測開始マーカーが変わるため、解析ツールはその記録を拒否できます。しかし、同じプロセス内のセーブ・ロードを挟んだ2つの累積記録が、同じゲームに属するかどうかは証明できません。このライフサイクル境界を修正すると、実行時の計測とスケジューラー・コールバックの管理主体が変わるため、今回のオフライン解析ツールの修正とは別の作業として扱います。

JSON には、現在の合成 `NavGridAdaptiveGateBenchmark` の規則（`dirty >= 20`、短辺の範囲 `>= 2`、長辺の範囲 `>= 4`）に対する `candidateGate` の上下限も出力します。実行時のヒストグラムは意図的に `dirty=16-23` のような粗い区分を使うため、その候補規則を満たす呼び出し数を常に正確に特定できるわけではありません。`eligibleCallsLowerBound` は確実に条件を満たす区分だけを数え、`eligibleCallsUpperBound` はしきい値をまたぎ条件を満たす可能性のある区分も含めます。`ambiguousCalls` はその差です。`--after-calls` モードでは、基準点より前の呼び出しではなく、新たなヒストグラム差分からこれらの上下限を計算します。これは対象となる処理割合の上下限であり、本番の処理経路の決定や性能の主張ではありません。前提条件の検査により、解析ツールのしきい値とベンチマークの定数を一致させています。

有効な記録には、起動メッセージの `NavGrid.UpdateGraph() resolved` と、その後の `target reached; aggregate sampling started`、および `calls` がゼロでない概要が必要です。FastTrack の有効な `PeterHan.FastTrack.PathPatches.NavGrid_UpdateGraph_Patch` を検出した場合、CycleTrim はサンプリングが無効であると報告し、FastTrack に置き換えられた処理を基準状態へ混ぜません。

Issue #25 に役立つ根拠を得るには、待機状態のコロニー、大量の建築・解体、ドアや自動化による経路構造の変化、動物の活動が多い状態など、複数の処理条件を分けて記録してください。記録ごとに ONI のビルドと有効な MOD の一覧も残します。各区分の割合を `NavGridAdaptiveGateBenchmark` に反映する条件付き計測では、完全記録モードと `--after-calls` の基準点を使ってください。通常の上位12区分の概要は、人が手早く確認するためだけのものです。この計測の目的は処理の分布と、対象処理に到達したことの確認だけです。計測機能自体の負荷を、FPS や CPU の高速化として報告してはいけません。
